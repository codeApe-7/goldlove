# 社交账号字段与校验设计

## 目标

让嘉宾端档案页按照现有高保真原型展示独立的“社交账号”卡片，并统一前后端字段语义：微信号必填，抖音号、抖音昵称、抖音主页链接选填。草稿允许不完整，提交审核时才执行必填校验。

## 当前问题

- `guest_profile`、草稿接口和版本快照已经包含微信及抖音字段，但 `profile_field_definition` 只初始化了基础资料与职业资料。
- 嘉宾端按字段定义动态渲染表单，因此没有定义的四个社交字段不会出现在 UI 中。
- 后端提交就绪校验只认识当前七个核心字段，无法把微信号识别为必填字段。
- 数据库字段代码使用 `snake_case`，嘉宾端草稿模型使用 `camelCase`；现有分组与取值逻辑混用两种命名，容易造成回显、完成度和提交载荷不一致。

## 方案

### 字段定义

新增 Flyway 迁移，把四个既有敏感字段注册为 `CORE` 字段：

| 字段代码 | UI 名称 | 类型 | 必填 | 顺序 |
|---|---|---|---|---:|
| `wechat_id` | 微信号 | `TEXT` | 是 | 80 |
| `douyin_id` | 抖音号 | `TEXT` | 否 | 90 |
| `douyin_nickname` | 抖音昵称 | `TEXT` | 否 | 100 |
| `douyin_profile_url` | 抖音主页链接 | `TEXT` | 否 | 110 |

这些字段继续使用 `guest_profile` 和 `profile_revision` 中已有的专用加密列，不改成动态字段，也不新增明文存储。

迁移使用按 `field_code` 判重的插入方式，以兼容已有本地数据库；若字段已存在，则更新其标签、存储类型、必填状态、启用状态、排序和提示文案，使环境收敛到本设计。

### 嘉宾端 UI

档案页保持原型的卡片式结构，在“职业与收入”和“个人影像”之间展示“社交账号”卡片：

- 卡片右上角显示当前已填写数量，例如 `1/4`。
- 微信号标签显示红色 `*`，输入提示为“请输入微信号”。
- 抖音号、抖音昵称、抖音主页链接不显示必填标记，允许留空。
- 四项均在当前页面直接编辑，不增加弹窗或二级页面。
- 布局、行高、分隔线、字体和右侧输入区域复用现有 `SectionCard` 与 `form-row` 视觉体系，保持黑白暖灰的高保真方向。
- 字段分组和表单状态统一以 API 的 `snake_case` 字段代码为索引；在保存请求与草稿回显边界显式映射到接口的 `camelCase` 属性。

### 前端数据与校验

- 新增集中式核心字段代码映射，负责 `snake_case` 定义代码与草稿/请求 `camelCase` 属性之间的转换。
- 字段渲染、分组、完成度和缺失项检查均使用同一套定义代码，避免局部硬编码产生分歧。
- `validateProfileForm` 继续只检查字段定义中 `required=true` 的项目，因此微信号会被前端拦截，其他社交账号不会阻止提交。
- 缺失提示优先显示字段中文标签，避免向用户展示 `wechat_id` 之类的内部代码。
- 保存草稿不执行完整性拦截；只有“提交审核”动作检查必填字段和头像。

### 后端提交校验

- `ProfileSubmissionReadinessValidator` 增加四个核心字段的取值判断。
- `wechat_id` 通过检查加密列与 HMAC 均存在来判定已填写。
- 三个抖音字段虽然可被识别，但因为字段定义为非必填，不进入缺失项结果。
- 草稿保存仍使用可选字段归一化逻辑，不对微信号做即时强制校验。
- 提交快照、审核详情和敏感字段加密流程保持不变。

## 错误处理

- 提交时微信号为空：前端提示“缺少必填：微信号”；绕过前端直接调用 API 时，后端返回 `PROFILE_VALIDATION_FAILED`，缺失字段包含 `wechat_id`。
- 抖音字段为空：草稿保存和提交均正常进行。
- 抖音主页链接非空但格式无效：沿用现有 URI/URL 格式校验并返回字段值错误。
- 字段定义迁移重复执行：不创建重复记录，结果保持幂等。

## 测试与验收

### 后端

- 提交就绪校验在微信号为空时返回 `wechat_id`。
- 仅填写微信号、三个抖音字段为空时不报告社交账号缺失。
- 字段定义接口返回四个社交字段，且仅 `wechat_id.required=true`。
- 相关 Maven 测试与完整后端测试通过。

### 嘉宾端

- 字段分组能把四个 `snake_case` 社交字段归入 `social`。
- 草稿回显和保存载荷正确映射四个社交字段。
- 前端校验只把微信号视为必填，并显示中文标签。
- Vitest、类型检查和 H5 构建通过。

### 视觉验收

- 在 390×844 和 320×720 视口检查社交账号卡片、必填标记、长主页链接输入和操作按钮。
- 卡片顺序、边距、分隔线和计数样式与原型一致。
- 页面无横向溢出，浏览器控制台无新增错误。

## 非目标

- 不新增其他社交平台。
- 不改变敏感字段加密算法、索引或权限模型。
- 不要求用户在保存草稿前填写微信号。
- 不修改管理端字段配置对核心字段身份和类型的保护规则。
